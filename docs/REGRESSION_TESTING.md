# Mettelo regression release gate

## Success criteria

A release is safe only when all of these are true:

- Critical public pages load without browser exceptions at phone, tablet and desktop widths.
- Navigation, CTA buttons, form validation, payloads and confirmation states remain functional.
- Guest, member, Project Architect and Admin permission boundaries remain intact.
- Contact, partnership, feedback, newsletter, project-interest and career journeys reach the expected isolated database records.
- Submitted records are visible in the matching Admin queue.
- Notifications or communication/outbox records are created where the product promises them.
- Destructive end-to-end tests are prevented from running against the production Supabase project.
- The complete release gate can run without a paid hosted staging database.

## Test layers

| Layer | Command | Purpose | Runs on |
| --- | --- | --- | --- |
| Static interaction audit | `npm run audit:interactions` | Finds dead buttons, forms without actions and missing API routes | Every PR and `main` push |
| Coverage audit | `npm run audit:regression-coverage` | Fails when a critical journey loses its implementation or test evidence | Every PR and `main` push |
| Phase 1 browser acceptance | `npm run test:phase1-browser` | Exercises authentication/onboarding and responsive acceptance criteria | Every PR and `main` push |
| Browser/API contracts | `npm run test:regression` | Exercises public pages, responsive forms, mobile menu, form payloads, validation and permission boundaries | Every PR and `main` push |
| Authenticated smoke | Part of `npm run test:e2e:staging` | Confirms member, Architect and Admin accounts can reach their protected workspaces | Trusted PRs and `main` |
| Isolated submission journeys | `npm run test:e2e:staging` | Proves browser → API → database → Admin queue → notification/communication against disposable local Supabase | Trusted PRs and `main` |
| Production build | `npm run build` | Confirms the exact Next.js production compilation still succeeds | Every PR and `main` push |

## Zero-cost isolated E2E setup

GitHub Actions uses the official Supabase CLI to start Postgres, Auth and Storage inside the hosted runner. No hosted staging project or paid Supabase branch is required.

The `staging-e2e` job:

1. checks out the repository and installs Node dependencies;
2. installs the Supabase CLI;
3. runs `scripts/prepare-local-supabase.mjs`, which creates an ephemeral `.supabase-ci/` workdir;
4. normalizes the two historical 8-digit baseline migration names so the clean local database applies them before later migrations;
5. adds `supabase/ci/20260809020000_missing_hosted_baseline.sql` for hosted objects that pre-date the repository migration history;
6. starts the local Supabase stack;
7. exports the generated local URL, anon key and service-role key only into that GitHub job;
8. runs `scripts/setup-local-e2e.mjs` to create separate disposable member, Project Architect and Admin identities plus a public project and published career role;
9. starts Mettelo locally against that stack and runs the existing authenticated/submission Playwright journeys with one worker;
10. destroys the Supabase stack at the end of the job.

The local fixture credentials committed in `.github/workflows/ci.yml` are intentionally non-secret because they authenticate only to the disposable loopback Supabase instance created inside that runner. They must never be reused for a hosted environment.

The service-role key generated by local Supabase is read only by the server/test process and is never injected into browser code or exposed as a `NEXT_PUBLIC_` service key. `scripts/check-e2e-config.mjs` still rejects the known Production project and, when `CI_LOCAL_SUPABASE=1`, requires the E2E Supabase URL to be `localhost` or `127.0.0.1`.

## Historical schema compatibility

The hosted Production database contains a small set of objects that pre-date the repository's canonical migration history. The CI compatibility baseline reproduces those objects so a clean, disposable test stack can exercise the current application without querying or mutating Production.

This does **not** declare the production migration-history provenance fully reconciled. The compatibility SQL is intentionally stored under `supabase/ci/` and applied only to the generated CI workdir. The remaining migration-history reconciliation is tracked in [Open issues](OPEN-ISSUES.md#p0-canonical-supabase-migration-history-still-needs-reconciliation).

## Repository protection

In GitHub branch protection for `main`, require the check named **Release gate** and require pull requests before merging. The release gate fails unless both the fast suite and isolated submission journey suite succeed.

If Vercel is connected directly to GitHub, keep Preview deployments for pull requests. Production remains protected by preventing an unverified PR from merging to `main`. For a stricter build-once/promote workflow, disable automatic production deployment and add a Vercel promotion job only after **Release gate**; that requires Vercel project and deployment credentials.

## Working locally

Fast, non-destructive checks:

```bash
npm ci
npx playwright install chromium
npm run audit:regression-coverage
npm run test:phase1-browser
npm run test:regression
```

To reproduce the isolated Supabase environment, Docker and the Supabase CLI are required:

```bash
node scripts/prepare-local-supabase.mjs
supabase start --workdir .supabase-ci
```

Use `supabase status --workdir .supabase-ci -o env` to obtain that disposable stack's local API/anon/service-role values, set the `E2E_*` variables to local-only identities, run `node scripts/setup-local-e2e.mjs`, start Mettelo at `127.0.0.1:3000`, then run:

```bash
npm run check:e2e-config
npm run test:e2e:staging
```

Never point the destructive E2E variables at Production. Stop the stack with `supabase stop --workdir .supabase-ci --no-backup` when finished.
