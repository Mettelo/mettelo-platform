## Audit conclusions before implementation

1. **Canonical run and membership architecture already exists.** `project_runs` and `project_members` remain the only authorities. Workstream 4 must not introduce `project_teams` or a second membership table.
2. **Phase 9 geometry is substantially correct.** Minimum drives readiness, target is nonblocking, maximum is guarded, Flexible Team can persist a threshold above one, and loss of minimum invalidates AUTO scheduling.
3. **Phase 10 formation is substantially correct but run-creation/reuse must be made race-proof across all admission/late-join/replacement paths.**
4. **The largest current correctness gaps are Admin lead assignment and delivery responsibility assignment.** Admin currently performs a non-transactional two-step Lead mutation and its “Save role” path updates application/project-role compatibility rather than canonical `project_member_responsibilities`.
5. **Readiness exists but is partly duplicated.** `phase11_project_start_readiness` is the intended canonical policy authority, while `project-team-readiness.ts` independently re-evaluates overlapping team/Lab/lead/responsibility state. Workstream 4 must converge these rather than add another readiness service.
6. **The start boundary is correctly shaped around `startProjectRun` → `phase9_activate_project_run`; Workstream 4 should harden/reconcile it, not replace it.**
7. **Production migration authority remains a release blocker until a monotonic reconciliation migration is deployed and verified.** Previous production inspection showed repository/runtime drift in historical Phase 8-11 functions; repository history must not be rewritten to repair that.
8. **No implementation changes are approved until this audit commit exists.** This document is that audit-first boundary.

## Implementation sequence unlocked by this audit

After this commit: canonical run/reuse hardening → membership idempotency → geometry reconciliation → responsibility authority → Project Lead authority → Admin/Member state → canonical readiness convergence → start/cron/late-join hardening → concurrency/RLS/migration/E2E/accessibility/downstream gates.
